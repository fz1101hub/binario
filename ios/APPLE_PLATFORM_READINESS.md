# Binario Apple Platform MVP: implementation and readiness

**Status:** the repository contains a production-oriented first iPhone MVP, a reusable pure Swift 6 core, and a coherent iPhone–Apple Watch XcodeGen project. The official Swift 6.4 Linux toolchain executes the package tests locally; Linux static checks validate the source graph and contracts. This environment cannot run XcodeGen's macOS binary, Xcode, iOS/watchOS simulators, signing, provisioning, or physical Watch Connectivity delivery, so those outcomes are deliberately not claimed.

## What is implemented

The iPhone application is a native SwiftUI app for iOS 17 and later. Its bundle identifier is `it.binario.ios`, its marketing version is `0.1.0`, and its build number is `1`. The app includes a journey planner, a station departures board («Partenze»), canonical station suggestions, local saved routes and trains, settings, privacy disclosures, data-source disclosures, empty states, Dynamic Type-compatible native controls, and accessibility labels. Italian is the development language, with complete English, German, French, and Spanish resources and machine-written, not yet native-reviewed Arabic, Hindi, Indonesian, Japanese, Korean, Burmese, Portuguese (Brazil), Russian, Thai, Turkish, Vietnamese, and Simplified Chinese resources (`docs/l10n/LOCALES.md`); the Watch string catalogue carries the same seventeen languages with CLDR plural forms. Station and provider names are never translated.

The Binario 2.0 colour tokens ([design system](../design/BINARIO_2_DESIGN_SYSTEM.md)) are defined once in `Resources/Assets.xcassets` with light and dark appearances: `AccentColor` (#2E7D32 / #9BDD9E) is the app-wide tint through `ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME`, `OnAccentColor` keeps the label of the prominent search button AA on that fill in both modes, `BrandGreen` (the #388E3C reference green) is used only for the decorative planner icon, and `StatusError` replaces the system red of validation messages, which is below AA on white. Views read them through `BinarioApp/BinarioPalette.swift`; no view hard-codes RGB values. These checks are static (`tests/test_verify_ios_project.py`); the Swift build runs in the `ios` CI job.

`BinarioKit` is a Swift 6 package with no third-party runtime dependency; it links only the platform SQLite and zlib libraries. It decodes the canonical 5,239-station repository asset in place instead of copying it, off the main actor, and exposes explicit loading, available, and unavailable states. The package validates that the station asset is identity-only and non-operational. A deterministic builder derives a compressed, verified SQLite schedule index from the ten checked-in GTFS packs. A reviewed policy locks each source ID to its HTTPS URL and `OPEN_DIRECT` access mode and records the licence shown in the Settings source list (`null` where the owner has not confirmed it yet); the manifest remains responsible for each refreshable archive SHA-256, and both policy and manifest enter the artifact fingerprint. Settings lists every pack of the index with attribution, last service day, licence and source page. Only complete rail trips touching a geographically verified canonical station identity are retained. Child/platform inheritance is rejected when explicit child coordinates contradict the parent identity; IANA timezones and monotonic stop times are validated by both builder and independent verifier. Large stop-time filtering uses disk-backed SQLite staging plus explicit retained-row and materialized-text budgets. At first launch the app validates metadata and SHA-256, performs bounded zlib decompression to a serialized atomic local cache excluded from backup, checks the SQLite schema and input fingerprint, then enables `SQLiteGTFSJourneyRepository`; every failure falls back to `FailClosedJourneyRepository`. Results are explicitly `PROGRAMMED` static data with their real feed attribution and manifest observation date. The provider never invents delays, platforms, cancellations, realtime status, or unverified station identity.

Saved routes are strictly validated and serialized only to the iPhone's local `UserDefaults` domain. Corrupt but syntactically valid JSON, duplicate route IDs, identical endpoints, and oversized fields fail closed. The app adds no account, cloud synchronization, analytics, advertising, location, microphone, background mode, background networking, credentials, cleartext endpoint other than Android's single ViaggiaTreno hop (see «Live data»), or signing identity. The 32-route bound is inherited from the main product's saved-route constraint.

### Network reliability, bikes on board and airport links

The planner shows the same unofficial network statistics as the Android app (shared specification of `stats_v1.json.gz`, schema `binario-punctuality-v1`). `ios/Scripts/sync-punctuality-stats.py` copies `app/src/main/assets/punctuality/stats_v1.json.gz`, after checking that it is a bounded gzip of that schema, to `ios/Resources/binario_punctuality_stats_v1.json.gz`, which XcodeGen bundles with the rest of `Resources` like the GTFS index; when the Android asset is absent the copy is removed, and `--remove` (`BINARIO_IOS_PUNCTUALITY_STATS=false ios/Scripts/generate-project.sh`) withdraws the statistics from the iPhone app alone. A build without the file hides every reliability line. The copy is generated, never committed: `ios/Scripts/generate-project.sh` and the Apple CI run the script before XcodeGen, so the weekly refresh of the Android asset needs no other step, and `tests/test_verify_ios_project.py` fails when a copy present in the checkout differs from the Android asset. `BinarioKit` reads the file once, off the main actor, with the CZlib gzip inflater and a strict streaming JSON reader: at most 8 MiB compressed, 64 MiB of JSON, 50,000 trains, 400 stops, 16 buckets and 16 levels of nesting; stop arrays of 5, 7 and 9 elements are valid, an implausible or `null` optional value is ignored without losing the stop, and an absent, corrupt, oversized or other-schema file gives no statistics. The rules are Android's: on time within 5 minutes for FR, FA, FB, EC, ES, ESC, EN and Italo and within 15 for the other categories, nothing below 5 samples at the stop, linear interpolation between buckets, the same number with another origin is another train, and a Trenord number of the timetables ("RE_11 - 2153") is matched by its train number. Results show «In orario 27 volte su 30 · ritardo medio 3 min» at the searched destination, the route punctuality (at least 20 samples, best and worst departure hours with 20 samples per band and 5 points apart) above the list and a «Più affidabili» order; the train detail adds the delay distribution («Senza ritardo», 1–5, 6–15, 16–30, oltre 30 min), the largest delay, the stop where the delay grows most, «Di solito al binario …» at the boarding stop (at least 5 days and 60% of the days with a platform) and the weekdays at least 15 points away from the stop's share (at least 4 samples, two at most), always with «Statistiche non ufficiali di Binario su dati ViaggiaTreno». Under a listed train on time in less than 70% of its samples at the destination (its own 5- or 15-minute limit, at least 5 samples), «Più puntuale: REG 16000 delle 08:12 · in orario 9 volte su 10» names another listed train leaving within 30 minutes before or after it, with at least 5 samples and at least 20 points more arrivals on time (shares compared exactly in integers; the closest departure first, then the earlier, the more punctual, the more samples), until a minute after its scheduled departure: Android's rule (`ReliableAlternatives` in `BinarioKit`), shown as a row of its own under the late train that opens the suggested train's detail and that VoiceOver reads as one sentence with «Mostra il treno delle 08:12» as its hint. The collector observes on ViaggiaTreno the trains of the Trenitalia pack, which the iPhone index does not include, and, since 9 November 2026, those of the Trenord pack, which it does: the statistics therefore cover the Trenitalia trains of the included packs (mainly the South Tyrol regional trains of the STA pack and some EuroCity trains) and, as the weekly refresh brings the days observed since then, the Lombardy regional and suburban trains of Trenord, matched by their train number. The file bundled at this commit (generated on 9 November, window 10 October – 8 November) does not hold Trenord trains yet.

The index (schema version 2) stores the GTFS `bikes_allowed` of each retained trip: 1 shows «Bici ammessa», 2 «Bici non ammessa», and an empty value, 0 or a feed without the column (Trenord, ÖBB, SNCF, Switzerland) stays unknown and shows nothing; the Italo pack, Android-only today, would be stored as unknown, as on Android, because Italo admits only folding bikes in a bag. «Collegamenti con gli aeroporti» lists Android's airport routes whose pack contributes trips to the index and whose two stations are bound to its stops: with the current packs, Milano Centrale and Milano Nord Cadorna ↔ Malpensa Aeroporto (Trenord). The delay-compensation notice of the Android detail is not ported yet: it needs an arrival delay verified by a live source at the searched destination, which the train detail now has (see «Live data»), but its wording and its rules (EU regulation 2021/782 thresholds) are a step of their own.

### «I miei treni» and «Affidabilità dei miei treni»

The star in the navigation bar of a train detail saves the train in «I miei treni», a tab of its own after «Tratte», or removes it (VoiceOver reads «Salva in I miei treni» / «Rimuovi da I miei treni»). As on Android a favourite is its number with its origin: here the station it is boarded at, so the same number saved from another station is another favourite. `FavouriteTrain` (`BinarioKit`) keeps what the detail shows as the bundled timetable published it on the day it was saved (number, operator, category, destination, scheduled time, bikes), with the boarding and searched stations and the date; a tap reopens that detail, measured at the searched destination as before. The number is validated as Android validates it (`BinarioDeepLink.FavouriteTrain`, `^[A-Za-z0-9]{1,12}$`) on the train number proper, so Trenord's «RE_11 - 2153», ÖBB's «S 2590» and SNCF's «K1+» are kept while a line name such as «Linea SASSARI-SORSO» gets no star; texts are bounded as the repository bounds them and the stations must make a valid query. At most 12 trains (Android's `FavouriteTrains.MAX`), newest first: a thirteenth is refused with «Puoi salvare al massimo 12 treni.» rather than dropping the oldest, and removing (swipe, VoiceOver action, star) is always possible. The list is a JSON array in `UserDefaults` (`it.binario.ios.favourite-trains.v1`); an unreadable value reads as no train, an invalid record is skipped on its own, duplicates and records beyond 12 are dropped, and a value over 64 KiB is ignored. Nothing is synchronised or sent to the Watch.

«Affidabilità dei miei treni», below the list, takes the first 8 favourites in their order (Android's `FavouriteTrainPunctuality.MAX_ROWS`) and shows each one's on-time share at its last stop with Android's rule (`ReliabilityMarks.favouriteStop`): the train serving the boarding station's code, measured at its terminus against its own 5- or 15-minute limit, from 5 samples; without a code, the only train with that number that runs; never a guess between several. A favourite without figures has no row; without the statistics file (`BINARIO_IOS_PUNCTUALITY_STATS=false`) or without any row the section is not shown. The rows say «Arrivo a Pavia: in orario 24 volte su 28 · ritardo medio 6 min» when the catalogue names the stop, VoiceOver adds «(statistiche non ufficiali)» and the section ends with the attribution. Android's «Registrato su questo telefono» and its trend «In miglioramento» / «In peggioramento» are both computed from the runs the Android phone records with its live lookups; the iPhone asks live data only for what is on screen and records no run, and the bundled file is a single 30-day aggregate per train and stop, so neither is shown here.

### «Partenze»

«Partenze» is the second tab (Viaggio, Partenze, Tratte, I miei treni, Impostazioni), where Android puts it right after «Pianifica»: what leaves a station now is a task of its own, asked without a destination, not a step of a route search, and a tab keeps the board one tap away with its own navigation stack, so a train opened from it does not replace the planner's results. The station is chosen with the planner's `StationPickerField` and catalogue (stations without timetable are marked as in the planner). The last one is remembered on the iPhone only, in `UserDefaults` (`it.binario.ios.departures-station.v1`, `StationBoardStationStore`): its catalogue identity as JSON, validated like the other stores (an invalid identity is not written; an unreadable, invalid or over-2-KiB value reads as no station), replaced by the next choice; the board footer and [PRIVACY.md](../PRIVACY.md) say so.

The board sits behind `StationBoardProvider` (`BinarioKit/StationBoard.swift`), a small `Sendable` protocol with one async query, so that a live source (ViaggiaTreno or RFI boards, the next step) can be added without rewriting it: `SQLiteGTFSJourneyRepository` is the first provider and stays the fallback of a live one, `FailClosedStationBoardProvider` answers while no validated index is installed, and each row (`StationBoardDeparture`) carries an optional `StationBoardLiveStatus` (expected time and delay, cancelled, actual platform, source and time of the observation) that the bundled timetable never sets; «Orari programmati statici. Non sono dati in tempo reale.» is shown while a listed row has no live value (`isScheduled`); with «Dati in tempo reale» on, the rows the live board lists carry their `StationBoardLiveStatus` (see «Live data»). The query runs off the main actor like the planner's and is bounded like it: for each agency time zone it reads today's service day and the runs of the earlier service days still to leave (yesterday's after midnight, GTFS times from 24:00; the index allows up to 168 hours), never the next service day's, with boarding allowed at one of the station's stops (`pickup_type = 0`) and the service calendar of the trip. A trip whose last stop is the station itself only arrives there and is no departure, as on Android; a trip calling twice is listed once, at its first departure from now. Each service-day query reads at most 4,096 rows, as the planner's does (`tests/test_verify_ios_project.py` checks that every station of the bundled index has fewer boarding rows per time zone), a page holds 20 trains (at most 50 per query) and «Più tardi» continues strictly after the last one listed, in the planner's order (departure, number, identifier), up to 200 trains; VoiceOver says how many were added. A row is listed until a minute after its scheduled departure, the planner's rule for a train still to be taken; the board is read again when the app comes back to the foreground, when its list empties and on a new Rome day. With no train left today it says «Non ci sono più treni oggi: primo domani alle 06:15» from the first train of the next service day, as Android's station board does; a station no stop of the index is bound to reads «Orari non inclusi», and timetables that end before today read as expired.

A row shows the scheduled time, the train named as the planner rows name it (`ReliableAlternatives.trainLabel`: «REG 2153», «RE_11 - 2153»), the destination, which is the trip's last stop, the operator and bikes on board as the planner shows them; VoiceOver reads it as one sentence, «08:12, treno REG 2153 per Bergamo, binario non disponibile», then operator and bikes. The index has no platform column (the GTFS `platform_code` is not stored, and the index format is unchanged), so no row shows a platform; the row would show one from a provider that publishes it. Coaches and replacement buses follow the planner's rule: the index keeps only the rail routes of the packs (`RAIL_ROUTE_TYPES` in the builder, with TFT's two railway lines published as buses) as the feeds publish them, and the board filters nothing more. As in the planner, a train that two packs both publish (a TILO train in the Swiss and the Trenord packs) is listed once per pack. A tap opens the train in `TrainDetailView` (with the row's live values until the run's own arrive), boarded at the board's station and measured at the train's last stop (its catalogue station, or for an uncatalogued stop an identity made of its pack and stop, `gtfs:<pack>:<stop>`): the star of «I miei treni» saves the number with the board's station, the identity a favourite has. No network reliability is shown per row: Android's station board shows none per train; it shows a station-level «Puntualità degli arrivi» card, which is not ported here.

### Live data

The owner approved live data on the iPhone (November 2026): the same public sources as Android, in the same order, with the bundled timetable as the fallback of every answer. The core is in `BinarioKit` (`LiveRailModels`, `LiveSourceHTTP`, `LiveSourceGate`, `ViaggiaTrenoLive`, `RfiLiveBoard`, `ItaloLive`, `LiveRailData`, `LiveStationBoard`); the screens are wired to it as described at the end of this section.

- **Order** (Android `LocalOnlyRailDataPolicy`). Train status by number asks ViaggiaTreno and Italo together (`trainNumberSearchProviders`): ViaggiaTreno's `cercaNumeroTrenoTrenoAutocomplete`, then `andamentoTreno` of each run of the asked day or the two before (at most 24, three at a time, 8 s in all; a known run, a board row's, is asked directly), and Italo's `RicercaTrenoService` for today's 3- to 5-digit numbers. The runs of both are kept, the verified copy of a run first, sorted by departure, as `TrainNumberSearchService` does; `LiveTrainStatusLookup.run(for:)` picks the asked one by its number, then the station code (origin, then a stop), then the origin name, and never guesses between two. A station's departures ask the RFI monitor, Italo and ViaggiaTreno together (`stationBoardProviders`): ten minutes back to six hours ahead, late trains from two hours back, Android's `StationBoardAggregateService` merging the rows of one train (same number, within five minutes, same destination, no known operators or runs of one source that differ) value by value with `RailSourceSelectionPolicy`'s scores: RFI for the row and the platform, the operator's source for expected times and states (ViaggiaTreno for Trenitalia, Italo for Italo). The RFI place comes from Android's names or the official selector (read once a day, or again a minute after a failed read or a page without stations, only when a board needs it), the Italo station code from the passenger page's list (the same cadence, after a failure only) or Android's reviewed codes.
- **Verified values** are Android's: ViaggiaTreno needs a cancellation, or a delay with an observation of the last five minutes (at most one ahead) of a train that has left; RFI a published delay or cancellation, a bare «RITARDO» being late without an expected time; Italo a fresh `LastUpdate` with a delay or a cancellation. A missing or old observation never becomes «0 min»; actual times stay the source's. A run is partially cancelled when ViaggiaTreno cancels some of its stops (`actualFermataType` 2 or 3).
- **Requests**: HTTPS only, with the honest User-Agent «Binario/0.1 (iOS; personal rail information client)» («personal realtime client» for ViaggiaTreno, as on Android), one ephemeral `URLSession` per request without cookies, credential storage or cache; 12 seconds for ViaggiaTreno, 10 for RFI and Italo; a body over 2 MiB is refused, never truncated; at most 300 rows per board and 400 stops per run, every number, date and length checked. Redirects come back to `LiveSourceClient`: the same resource on the same HTTPS host, the HTTPS variants of Android's ViaggiaTreno realtime client, and the single cleartext hop; anything else is refused. The alternate HTTPS host `viaggiatreno.it` (the apex) also receives a ViaggiaTreno request when `www.viaggiatreno.it` redirects it elsewhere over HTTP, as Android's realtime client does; `PRIVACY.md` names both hosts and both User-Agents.
- **Manners** (`LiveSourceGate`): one request per resource every 30 seconds (RFI 20), shared by concurrent callers, a failure remembered for as long; the first refusal (HTTP 403 or 429) pauses the whole source, for its `Retry-After` up to an hour or for a minute doubling up to 15; three failures in a row pause it too (a device without a connection, or a request with no answer at all before its time limit, is not counted against the source), after a pause one request is let through while the others wait as if paused, and only an answer to a request sent since the pause ends it. Nothing is retried by itself, nothing is rotated. `LiveSourcePauses` lists the pauses for a status line; every failure is a typed `LiveUnavailableReason`, and every call is cancellable.
- **App Transport Security**: `Configuration/Binario-Info.plist`, merged by Xcode with the generated keys (`INFOPLIST_FILE` next to `GENERATE_INFOPLIST_FILE` in `project.yml`), holds the only exception, insecure HTTP loads for www.viaggiatreno.it without subdomains, as Android's `network_security_config.xml`; `tests/test_verify_ios_project.py` pins both. App Review gets its justification in the review notes (`docs/store/APP_STORE_SUBMISSION.md` §4 and §5: ViaggiaTreno's public service redirects some HTTPS requests to the same resource over HTTP; read-only public data, no credentials or user data). The export-compliance key stays `NO`: the only encryption is the operating system's HTTPS.
- **Tests**: XCTest without network, on `BinarioKit/Tests/BinarioKitTests/Fixtures` (a recorded ViaggiaTreno run of FR 9558, the payload shapes of Android's adapter tests) and fake transports: redirects, refusals and pauses, cancellation, malformed payloads, runs across midnight, the source order and the merge.
- **Overlay**: `LiveOverlay` matches a bundled row with its live row by `NetworkReliability.numberKey` and a scheduled time within five minutes; `LiveOverlay.stationBoard(_:with:at:)` gives «Partenze» rows their `StationBoardLiveStatus` from a merged board (only values still live, named after the source of the expected time; a cancellation without an expected time), every other row staying «orario programmato». Not ported: Android's route searches built from boards, arrival boards, route-change wording, Italo's HTML board, per-train notices and the Swiss board. `StationBoardLiveStatus` also names the source of the row (`source`), the source of its platform when another one gave it (`platformSource`, RFI's platform under ViaggiaTreno's time) and a bare «RITARDO» (`lateWithoutMinutes`), so a row can say where each value comes from.
- **Wiring** (`AppModel`, `LiveTexts`). One `LiveRailData.standard()` for the whole app, so every screen shares its sources' gates. Requests are made only in the foreground and only for the screen on display: each screen tells the model when it appears and disappears, `RootView` cancels every request on its way when the app goes to the background and lets the screen on display ask again when it comes back, and a minute tick stops showing values older than five minutes (Android's recency limit; the screen keeps its timetable until it is refreshed). Nothing is asked by itself on a schedule, nor in the background, nor by Watch Connectivity; the Watch snapshot stays the programmed one. Every load follows the board's stale-response pattern (a request ID bumped by each request and by the screen going, the model's own `Task` cancelled), so an answer for a station, a search or a train left behind never reaches the next one.
  - **«Partenze»**: the merged live board of the station (`departures(LiveDeparturesRequest(station:from:))`, from the current minute) over the bundled rows (`LiveOverlay.stationBoard`), asked when the tab appears, comes back to the foreground, changes station, or with pull-to-refresh and the «Aggiorna» button; «Più tardi» rows get the same board's values. A row shows «prev. 08:17 · +5 min» (Android's `expected_time_short` and `delay_minutes`), «In orario», «Soppresso» or «In ritardo (minuti non pubblicati)», the actual platform, and «Fonte: ViaggiaTreno · Binario da RFI · Rilevato alle 08:15»; VoiceOver reads the live state inside the row's sentence. The footer says «Dati in tempo reale da RFI e ViaggiaTreno», «Dati non disponibili in tempo reale» when every source failed (the rows stay the timetable's), and «ViaggiaTreno in pausa fino alle …» from `LiveSourcePauses`. The scheduled time is always printed as such; only a source's value is called «previsto» or «effettivo».
  - **Planner**: for a search leaving from three hours before to three hours after now (Android's `JourneyLiveCandidates` window), one live board request for the origin, whatever the number of trains; each listed train is placed in time from its "HH:mm" as the Watch places it and matched by its number proper within five minutes (`LiveOverlay.departure`): delay, cancellation and platform at the origin, with their source. A failure, a search outside the window or a changed input leaves the results as they were; the disclosure stays for the trains without a live value.
  - **Train detail**: for a train leaving within the window, the run by its number proper (`NetworkReliability.numberKey`: «2153» of «RE_11 - 2153») and the boarding station's code (`trainStatus(LiveTrainStatusRequest(number:serviceDate:stationCode:))`, then `lookup.run(for:)` among the runs that call at the boarding station within two hours of its timetable departure, Android's `SAME_RUN_TOLERANCE`, so yesterday's run of the same number is never shown, then `LiveOverlay.stop`): the run at a glance («In ritardo di 7 minuti», «In orario», «Soppresso», «Parzialmente soppresso», «Fermata saltata», or «Stato operativo non verificato» without a recent observation of a train that has left), the expected departure and platform at the boarding station, «Ultimo rilevamento», the source, then every stop with its scheduled time, the source's actual («Effettivo») or expected time, delay and platform, passed and cancelled stops, each read as one sentence. Asked when the detail appears and on pull or «Aggiorna»; until it arrives the values of the row the detail was opened from stand in, and the run's own state wins over them. The star of «I miei treni» is unchanged. A favourite opened from «I miei treni» means today's run.
  - **«I miei treni»**: today's state of the first 8 favourites (Android's `MAX_ROWS`) leaving within the window, asked one after the other only while the tab is on screen (appearance, foreground, pull, «Aggiorna»), with its source and observation time under each train.
  - **Settings**: Android has no switch for its live sources; the iPhone adds «Dati in tempo reale», on by default, in `UserDefaults` (`it.binario.ios.live-data-enabled.v1`, `LiveDataPreferenceStore`: only a boolean the app wrote counts, anything else reads as on). Off, every request on its way is cancelled, every live value goes and no screen asks anything: the app is the bundled timetable alone, as before. Below it, the sources the iPhone asks and what each receives: ViaggiaTreno a train number, a station code, the date and time; RFI a station's public place ID; Italo a train number or an Italo station code; no account, identifier or location, the device's IP address seen as by any website, answers kept in memory only. `PRIVACY.md` («Dati in tempo reale») and the App Store notes describe the same.
  - **Texts**: Android's strings where they exist (`run_status_*`, `delay_minutes`, `expected_time`, `expected_time_short`, `data_status_source_paused`, `data_status_unavailable`, `route_change_source`, `operational_status_unverified`, `trains_widget_delay_accessibility`…), in the 17 languages with CLDR plurals for «In ritardo di N minuti»; the new ones («Dati in tempo reale da …», «Rilevato alle …», «Effettivo …», «Binario da …» and the Settings texts) machine-written for the twelve added languages like the others.
  - **Tests**: `BinarioAppTests` drives the model with fake providers, no network: the overlay into «Partenze» rows (sources, platform source, spoken sentence, expiry, failure, hidden board), an answer for a station left behind, planner results within and beyond the window, the detail's own run against another day's, favourites capped at 8 and asked only while visible, and the switch (off asks nothing, on asks the screens on display, off again clears every value). `tests/test_verify_ios_project.py` pins the rules statically.


## Apple Watch integration

Watch sharing is local, persisted, and **off by default**. The iOS app activates Watch Connectivity during bootstrap, keeps only the latest validated pending operation until activation completes, and publishes the existing Wear snapshot v1 contract under `binario_snapshot_json`. `WearSnapshotEncoder` rejects unsupported versions, non-iOS producers, invalid timestamps, mismatched or excessive time-to-live values, more than two services, invalid field lengths, out-of-range delays, incoherent unavailable states, and payloads over 8,192 bytes before the session is touched. Disabling sharing replaces any pending snapshot with the explicit transport-level `binario_snapshot_clear` signal; the Watch gives that revocation precedence, clears shared storage, and reloads widgets. Publication errors and unsupported sessions are surfaced without claiming physical delivery. A successful GTFS query for now publishes at most two services marked `PROGRAMMED` with static-data disclosure and real provenance: only trains that have not left yet, with an expiry two minutes after the last one sent; a failed query, or one whose listed trains have all left, publishes a short-lived, service-free `UNAVAILABLE` snapshot. The planner searches from the current time unless the user picks one, and moves its default time to now (searching again when a result is on screen) whenever the app becomes active; it picks and shows times in the timetable zone (Europe/Rome) with a caption when the device clock differs. The Watch route title is the station names, with the route identifier only when another catalogue station shares a name. A snapshot held back because no Watch app could receive it is delivered when Watch Connectivity reports a change of Watch state, and turning sharing on publishes the search for now already on screen. The Watch's "Aggiorna" message (`binario_refresh_request`) is acknowledged at once and makes the app repeat the route of its last search for now without changing what the planner shows. Tapping a saved route opens the planner on it and searches from now.

«Mostra su Watch» (touch and hold, or swipe right on, a saved route) pins one route to the Watch; its identifier is kept in `UserDefaults` (`it.binario.ios.watch-pinned-route.v1`) and dropped with the route. With sharing on, the iPhone publishes the pinned route's next trains whenever no search for now owns the Watch: at launch once the index is open, after the planner input changes (instead of the revocation), when sharing is turned on and when the Watch asks for a refresh. A search for now still takes the Watch over until the input changes; removing the pin clears the Watch it was shown on. The app declares no background mode and schedules nothing: `BinarioApp` creates the model, and with it the Watch Connectivity session, at launch rather than with the first window, because Watch Connectivity launches the app in the background for «Aggiorna»; the request is held while the index opens and the work runs inside a `UIApplication` background task so the context is sent before the app is suspended. The Watch sends the same empty request once when its app opens with no train to show.

`ios/project.yml` owns the integrated Apple graph in Swift language mode 6: the iPhone app embeds a modern single-target `BinarioWatch` application (`it.binario.ios.watchkitapp`); the watch target embeds its WidgetKit extension (`it.binario.ios.watchkitapp.widgets`); `WKWatchOnly` is disabled; and `WKCompanionAppBundleIdentifier` is `it.binario.ios`. Marketing version and build number are shared by all embedded products. The iPhone, Watch app, and Watch widget each carry a privacy manifest appropriate to their `UserDefaults` scope (`CA92.1` for app-only preferences and `1C8F.1` for the app-group cache). The previous standalone `apple-watch/project.yml` retains its independent `it.binario.watch` identity; it has not been silently reinterpreted as an integrated build. Bundle identity and WidgetKit syntax now have local static guards, **not** an Xcode archive or installation proof.
